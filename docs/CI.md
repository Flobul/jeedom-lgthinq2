# CI locale du dépôt

Ces fichiers sont des outils de développement uniquement et ne sont pas chargés par Jeedom en phase d'exécution.

Les six workflows coordonnent la syntaxe PHP et PHPStan, la syntaxe frontend/ESLint/CSS, la structure Jeedom, la sécurité et l'audit des dépendances, ainsi que la génération i18n. Certains défauts de syntaxe, métadonnées mal formées, secrets à haute confiance et vulnérabilités exploitables sont bloquants. Les constats de PHPStan, d'harmonisation du style, de migration jQuery et de convention Jeedom débutent comme des avertissements explicites, sans exclusions larges ni `continue-on-error`.

La CI statique ne vérifie pas les largeurs des tuiles rendues, la mise en page visuelle ou le comportement d'exécution « Modification en cours… » ; ces aspects nécessitent des tests navigateur.

La traduction utilise le core Jeedom épinglé et `jeedom/jeetranslate`, conserve les valeurs manuelles existantes, valide les placeholders et ouvre une PR révisionnable limitée à `core/i18n/*.json` et `plugin_info/info.json`. Secret de dépôt requis : `DEEPL_API_KEY`. Les PR de type « fork » ne valident que les traductions actuelles et ne reçoivent ni secrets ni permissions d'écriture.

`market_badges.py` régénère le bloc de badges du market Jeedom (note, prix, remise, achats, téléchargements, commentaires) dans `README.md`, entre les marqueurs `market-badges:start` et `market-badges:end`. Le workflow `Market badges` s'exécute après un push sur la branche par défaut, chaque lundi à 04:17 UTC et sur demande. Il commite uniquement lorsqu'une valeur a réellement changé. Le commit généré contient `[skip ci]`, pour qu'un compteur de téléchargement changeant ne relance pas la CI complète du dépôt.

Les plugins publiés épinglent `"market": {"id": <n>}` dans `ci-config.json`, évitant la découverte HTML fragile du catalogue lors des rafraîchissements. Le `logicalId` renvoyé par le market est vérifié à chaque exécution contre l'identifiant du plugin dans `plugin_info/info.json`, pour qu'un épinglage obsolète ou erroné ne puisse pas publier les statistiques d'un autre plugin. Les plugins non encore publiés conservent la découverte automatique du catalogue ; chaque candidat n'est accepté qu'après le même contrôle de `logicalId` (`LG ThinQ Local` ne peut donc jamais hériter des badges de `LG ThinQ`).

Le workflow écrit uniquement pour les événements planifiés ou manuels de confiance et pousse vers la branche par défaut ; les pushes vers les branches de fonctionnalités sont ignorés. GitHub Actions utilise des versions majeures explicites (`actions/checkout@v7`, `actions/setup-python@v7`). Le workflow exécute `test_market_badges.py` avant de modifier le README et rebase avant de pusher. Une configuration invalide, des marqueurs mal formés, une recherche ambiguë ou une panne du market produit une notification ou un avertissement et laisse `README.md` intact : un rafraîchissement de badge ne doit jamais corrompre le README ni mettre le dépôt en rouge parce que le market externe est indisponible.

`readme_badges.py` répare les badges de dépôt d'un dépôt **privé**. shields.io interroge l'API GitHub sans authentification, donc chaque badge `img.shields.io/github/*` affiche « repo not found » sur un dépôt privé — un badge `dynamic/json` pointant vers `api.github.com` échoue de la même façon. Le `GITHUB_TOKEN` fourni au workflow `README badges` *peut* lire le dépôt, donc le script résout la licence, le langage principal, le dernier commit, les issues ouvertes et les pull requests ouvertes une fois et réécrit ces cinq routes en badges shields.io statiques. Aucun appel à l'API GitHub n'est fait lors de l'affichage du README, donc les badges s'affichent pour tout le monde, dépôt privé ou non.

`github/issues` est un préfixe de `github/issues-pr`, donc les routes sont réécrites de la plus longue à la plus courte avec un garde-fou final ; sans cela, le badge des pull requests serait silencieusement remplacé par celui des issues. Les comptages d'éléments ouverts proviennent du numéro de page `rel="last"` d'une requête `per_page=1`, donc une seule requête donne le total. Le workflow suit les mêmes conventions que le travail des badges du market : versions d'action épinglées, exécution d'un test unitaire avant l'écriture, `[skip ci]` sur le commit, rebase avant push et `exit 0` avec un avertissement en cas de problème API.

`report_ci.py` s'exécule dans le travail `report` de `ci.yml`, après tous les autres travaux et avec `always()`, uniquement sur la branche par défaut. Il lit les travaux de l'exécution courante ainsi que les annotations de check-run du commit, écrit le résumé dans `GITHUB_STEP_SUMMARY` et crée ou met à jour une seule issue roulante intitulée `[CI] Rapport qualité automatique` au lieu de laisser une issue par échec. Lorsque l'exécution est propre, il commente et ferme cette issue. Les exécutions `pull_request` sont exclues car les branches de fork sont non fiables et leurs annotations ne sont pas exploitables dans l'issue de la branche par défaut. Des variables d'environnement manquantes font sortir `2` ; une erreur API affiche un avertissement et sort `0`, pour qu'un échec de rapport ne masque jamais une CI verte.

`check-php.yml`, `ci-config.json`, `phpstan.neon` et `translation.yml` portent les valeurs propres à chaque plugin et sont les seuls fichiers attendus comme différents entre les dépôts : la matrice PHP, la liste des branches, l'entrée de scan `3rdparty/Capabilities.php` et la liste de langues i18n déclarées. Tous les autres fichiers CI sont strictement identiques dans toute la flotte, donc une correction faite dans un dépôt peut être copiée dans les autres sans adaptation.
